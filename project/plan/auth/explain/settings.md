設定する場所は 3 つです。**手順そのものは [manual/](/project/plan/auth/manual/index.md) にあります。**
ここでは「それが何のための設定か」を説明します。

# 1. Supabase 側

| 設定 | 何のためか |
| :- | :- |
| プロジェクトの作成 | 通行証を発行する受付を用意する |
| **Custom Access Token Hook** | 通行証に `x-hasura-*` を書き足す。**これが無いと全件が弾かれる** |
| 検証用ユーザーを 2 人 | 「他人のメモが見えない」ことを確かめるため。1 人では確かめられない |

Hook は SQL の関数として書きます。**アプリのテーブルを読まない作り**にしてあるのが要点です。
Hook は Supabase 側のデータベースで動くため、ローカルのメモのテーブルは見えないからです。

# 2. Hasura 側

| 設定 | 何のためか |
| :- | :- |
| `HASURA_GRAPHQL_JWT_SECRET` | 通行証の検証方法。**鍵の置き場所（JWKS の URL）**を教える |
| `user` ロールの権限 | 「自分の行だけ」という条件を定義する |
| Actions の権限 | ログインユーザーが書き込み処理を呼べるようにする |
| API の上限 | 極端に重いクエリを弾く |

`HASURA_GRAPHQL_UNAUTHORIZED_ROLE` は**あえて設定していません。**
設定すると、通行証が無いリクエストもその権限で通ってしまうためです。

## 鍵の持ち方

Hasura は**公開鍵だけ**を Supabase から取得します。秘密鍵は Supabase 側にあり、
Hasura は持ちません。**「署名を作れないが、検証はできる」**状態です。

これを**非対称鍵**といいます。仮に Hasura が乗っ取られても、通行証を偽造されません。

# 3. アプリ側

| ファイル | 入れるもの |
| :- | :- |
| `.env` | プロジェクト ID、公開キー、Hasura と NestJS が共有するシークレット |
| `apps/api/.env` | 上と**同じ**共有シークレット、データベースの接続先 |

## 公開してよい値・いけない値

| 値 | 公開してよいか | 理由 |
| :- | :- | :- |
| `SUPABASE_PROJECT_REF` | **よい** | URL の一部として誰でも見える |
| `SUPABASE_PUBLISHABLE_KEY` | **よい** | ブラウザに載せる前提で作られている |
| `HASURA_ACTION_SECRET` | **だめ** | 書き込み処理の関門になっている |
| `HASURA_GRAPHQL_ADMIN_SECRET` | **だめ** | 全権限を持つ |
| service_role キー | **絶対にだめ** | 全権限。今回は使わない |

> [!CAUTION]
> `VITE_` で始まる変数は**ビルド結果に埋め込まれ、ブラウザから読めます。**
> 秘匿値を入れないでください。

`.env` は `.gitignore` 済みでコミットされません。

# 設定を間違えたときの見え方

**「エラーが出ない代わりに 0 件になる」**のが厄介な点です。

| 症状 | 原因 |
| :- | :- |
| Hasura が起動しない | `SUPABASE_PROJECT_REF` が未設定（鍵を取りに行けない） |
| ログインできるがメモが 0 件 | **Hook が未設定**（通行証に権限が書かれていない） |
| ログインできるがメモが 0 件 | シードの所有者が実ユーザーと違う |
| 書き込みだけ 401 | `HASURA_ACTION_SECRET` が両側で食い違っている |
